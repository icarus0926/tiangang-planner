# 天罡 Agent Memory 文档设计

## 目标

为 `tiangang-planner` 建立一套可随仓库版本控制、适合新 Agent 渐进加载的项目记忆。文档必须以当前源码为事实来源，覆盖架构、领域语义、API、前端交互、开发验证、运行运维与已知风险，并明确哪些行为不能在后续迭代中被无意破坏。

## 方案比较

### 方案 A：单个巨型 `MEMORY.md`

优点是入口单一；缺点是很快膨胀，Agent 每次都要加载与当前任务无关的内容，且架构、API、交互和运维容易混在一起。

### 方案 B：`AGENTS.md` 短入口 + `docs/agent/` 模块化事实页（采用）

根目录 `AGENTS.md` 只保留强约束、验证门和阅读路由；`docs/agent/` 按关注点拆分。Agent 可先读入口，再按任务只加载 1–2 个相关文档。当前状态与技术债单独记录，避免把临时事实写进稳定的领域模型。

### 方案 C：仅增加源码注释

注释最接近实现，但无法提供跨文件数据流、端到端交互语义、发布流程和变更矩阵，不足以承担项目记忆。

## 文档结构

```text
AGENTS.md
docs/agent/
├── README.md                 # 阅读顺序与任务路由
├── ARCHITECTURE.md           # 组件、文件责任、启动与数据流
├── DOMAIN_MODEL.md           # 表结构、状态机、时间与完成语义
├── API_REFERENCE.md          # 14 个路由、校验、事务与副作用
├── FRONTEND_GUIDE.md         # 页面、状态、渲染模块、甘特与图谱交互
├── DEVELOPMENT_WORKFLOW.md   # 环境、测试、UI QA、迁移、发布、安全
└── PROJECT_MEMORY.md         # 当前基线、决策记录、风险与后续改进
```

另外保留本设计与实施计划在 `docs/superpowers/`，说明这套 Memory 的生成依据和维护方法。

## 单一事实源

- 数据库结构：`db.js` 中 `SCHEMA`。
- 后端行为与 API：`server.js`。
- 前端页面与交互：`public/index.html`。
- 可执行契约：`test.mjs`。
- 一次性旧系统迁移：`migrate/*.mjs`。
- `README.md` 面向使用者；若与上述源码冲突，以源码和测试为准，并在本次同步修正已确认的漂移。

## 维护原则

1. 不在文档中记录口令、Notion token、数据库内容或个人任务明细。
2. 稳定语义与当前快照分离；动态数据量只能写“核验日期 + 非契约快照”。
3. 不用容易漂移的源码行号作为主要定位，优先引用文件名和函数/路由名。
4. 修改状态机、字段点亮、完成冒泡、甘特排序或标签持久化时，必须同步对应 Agent 文档。
5. 文档完成需通过：链接存在、关键路由/状态覆盖、`npm test`、`git diff --check`。

## 自审结果

- 无 `TBD`、`TODO` 或待定结构。
- 文档边界与当前“少文件、零构建”架构一致，不要求重构产品代码。
- 明确区分稳定契约与已知风险，避免把现存缺陷包装成设计意图。
